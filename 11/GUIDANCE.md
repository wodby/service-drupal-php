# Drupal on Wodby

What Wodby sets up for a Drupal application on this service, in addition to the PHP service it is based on. Check it before changing `settings.php`, connecting Drupal to a cache or search service, or moving the files and configuration directories. Adding a second copy of this configuration to the codebase is the usual mistake.

## What Wodby generates

The Drupal PHP container writes two files on every start, from its environment variables:

- `$CONF_DIR/wodby.settings.php` (normally `/var/www/conf/wodby.settings.php`)
- `$CONF_DIR/wodby.sites.php`

They are outside the codebase and are rewritten on each start, so never edit them and never copy their values into the repository. `sites/<site>/settings.php` includes the first one in a block marked `// Generated by Wodby.`, appended at the end of the file by the build or by workspace setup. Keep that block, and keep it after the project's own settings. With a site directory other than `default`, `sites/sites.php` includes the second file, which maps the environment's hosts to that site.

Read the generated file to see exactly what applies to this environment. It holds passwords: quote setting names, not secret values.

## What it configures

| Area | What Wodby sets | From |
| --- | --- | --- |
| Database | `$databases['default']['default']` host, port, name, user, password, driver | `DB_*`, set by the linked database |
| Hosts | `trusted_host_patterns` for every host of the environment | `WODBY_HOSTS` |
| Proxy | `reverse_proxy` and `reverse_proxy_addresses` | request, `DRUPAL_REVERSE_PROXY_ADDRESSES` |
| Hash salt | `hash_salt`, when the project sets none | `DRUPAL_HASH_SALT` |
| Files | public `sites/<site>/files`, private `$FILES_DIR/private`, temporary `/tmp` | `FILES_DIR` |
| Config sync | `config_sync_directory` under `$FILES_DIR/config/`, when the project sets none | `DRUPAL_FILES_SYNC_SALT` |
| Cache | Redis connection and cache backend, under the conditions below | `REDIS_*` |
| Search | Search API Solr server credentials | `SOLR_CLOUD_*` |

The database, file paths and trusted hosts are set by Wodby whatever the project's settings say. The hash salt and the config sync directory are only defaults: a project that keeps configuration in Git sets its own `config_sync_directory` above the Wodby block, and Wodby leaves it alone.

`sites/<site>/files` is a link to the files volume (`$FILES_DIR/public`). Uploaded files live on that volume, not in the codebase and not in the image.

## Redis or Valkey cache

The connection and the cache backend are configured by Wodby when all of these hold:

1. The stack's Redis or Valkey service is enabled and linked to the Drupal PHP service. `REDIS_HOST` is then set in the container.
2. The `drupal/redis` module is in the codebase (`composer require drupal/redis`) under `modules/contrib` or `modules`.
3. The Drupal PHP service has the environment variable `DRUPAL_ENABLE_REDIS_CACHE` set to a non-empty value, for example `1`.

Then the generated settings point `redis.connection` at the service with the PhpRedis interface, make Redis the default cache backend and load the module's `example.services.yml`. Do not add Redis settings to `settings.php`. What is left for the project is to enable the module (`drush en redis`) and rebuild caches.

A missing condition is the usual reason "Redis is not used": check `REDIS_HOST`, the module directory and `DRUPAL_ENABLE_REDIS_CACHE` before changing anything else.

## Solr

With a linked Solr service, Wodby overrides the username and password of one Search API Solr server in configuration: the server whose machine name equals `SOLR_CLOUD_SERVER`, which is the Solr service's host name in the environment (normally `solr`). Give the Search API server that machine name, and do not store the password in exported configuration or in `settings.php`. The rest of the server's configuration, such as its connector, host and collection, belongs to the project's own Drupal configuration.

## Changing what is wired

Service connections come from the environment's services and their links, not from code:

- To add a cache or search service, enable it in the environment's services and make sure it is linked to this service, then deploy.
- A variable such as `DRUPAL_ENABLE_REDIS_CACHE` is set on this service in the environment. It reaches the container, and the generated settings, with the next deployment of the service.
- Code changes (`composer require`, enabling a module, exported configuration) go through the repository as usual.

## In a development workspace

A workspace runs the same image against the live checkout, with the same generated files and the same variables. Differences that matter:

- Workspace setup appends the include to the checkout's `settings.php` in a form that is safe to commit: it includes the file only where it exists.
- The checkout's `sites/<site>/files` becomes a link to the files volume. Setup refuses when that directory is tracked by Git or not ignored; fix the repository instead of working around it.
- The generated files are rewritten when the container starts. After enabling a service or changing a variable, deploy the environment and check `$CONF_DIR/wodby.settings.php` again.
- `drush` and `composer` run from the checkout with the same environment as web requests.

## Check the result

Confirm against the running environment, not the code alone:

- `drush status` shows the database connection.
- `drush php:eval 'var_export(\Drupal\Core\Site\Settings::get("cache"));'` shows the cache backend in use.
- The Search API server page, or `drush search-api:server-list`, shows whether Solr is reachable.
